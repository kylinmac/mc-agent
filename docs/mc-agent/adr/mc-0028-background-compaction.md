# MC-ADR-0028: 后台预生成压缩摘要

**Status:** Accepted（2026-11-11 用户确认按建议实现）
**Date:** 2026-11-10
**Deciders:** 产品负责人
**来源:** [kylinmac/mc-agent#121](https://github.com/kylinmac/mc-agent/issues/121)

## 背景

自动压缩只在回合边界内联执行：用量到安全预算的 90% 时，下一次模型请求之前先发摘要请求，用户和模型都等它完成（`packages/agent-runtime/src/context-budget.ts`，`runtime.ts` 的 `prepareNextTurn()` 与新提问入口）。R20 把单次压缩从十分钟级降了下来，但等待仍在关键路径上。

R31 上线后，70% 时会先清理旧工具结果。只有清理也压不住时用量才会继续涨到 80% 以上，所以需要摘要的会话变少了，但真到那一步时等待依旧。

源码确认的两个事实决定了方案形状：

- 检查点以 `throughMessageId` 为界：重建上下文时，摘要条目插在该消息之后，**之后的消息原样保留**（`entriesWithCompaction()`）。所以“摘要覆盖到较早的边界，边界之后的新消息保持原文”不需要新的数据结构。
- 生成与安装已经分开：`buildCheckpoint()` 不落盘、不改会话状态，`installCheckpoint()` / `persistCheckpoint()` 才安装，并在安装前检查体积。

上游历史（源码与提交记录确认）：上游曾实现过后台预计算（提交 `c569388b7`，上游 ADR 0061），随后在 `438b7c262` 移除，理由是与 Codex 行为保持一致（Codex 只在回合边界内联压缩），并写明“代价是压缩又能被感觉到”。移除不是因为缺陷。本记录在 Fork 里重新引入，默认关闭，所以默认行为仍与上游一致。

2026-11-11 安装版基线（见[压缩后的上下文恢复](../compaction-context-restore.md)）：25 次压缩，单次中位耗时约 149 秒，全部落在用户等待的关键路径上。

## 决定

1. **预备线 80%。** 回合边界上用量达到安全预算的 80%、低于 90% 且当前没有摘要在生成时，以当时的持久边界为界启动一次后台摘要。当前回合照常继续，不显示阻塞状态。
2. **安装时机不变。** 仍在原来的 90% 判断处。此时若后台摘要已完成且有效，直接安装：摘要覆盖到预生成时的边界，其后的消息保持原文。安装后必须低于自动压缩线，否则丢弃这份摘要，走现有内联压缩。
3. **未完成就到线。** 到 90% 时后台摘要还在生成：等它完成（沿用现有静默保护和 Stop），不另起一个请求。等待期间显示现有的压缩进度。
4. **失效即丢弃并取消请求。** 条件：边界及之前的历史被改写（`session.replaceMessages`、回滚、fork）；模型或推理等级切换；手动压缩或模型调用 `new_context`；压缩开关被关闭；会话切换或运行时销毁；用户 Stop（Stop 只取消正在等待安装的那次，不影响下一次预生成）。
5. **同一时刻最多一个摘要请求。** 后台与内联互斥；后台请求在途时内联路径复用它，不并发。
6. **请求与用量沿用现有通道。** 认证、请求头、会话关联、静默保护、重试策略、截断短重试都不变；用量记到触发它的回合并计入检查点。被丢弃的摘要的用量仍然计入统计，不隐藏。
7. **失败等于没有预生成。** 后台摘要失败不提示用户、不重试第二次，到 90% 时按现状内联压缩并沿用现有失败恢复。
8. **开关。** 新增设置“提前在后台准备压缩摘要”，首个版本默认关闭；跟随自动压缩总开关。打开后被丢弃的次数和用量写入日志（只含计数和 token 数），用来判断是否值得默认开启。
9. **与 R31 的顺序。** 清理先于预备线判断：一次清理把用量降回 80% 以下时不启动后台摘要。后台摘要读取原始工具结果（按既有上限截短），不读占位。

## 不做

- 不改摘要提示词、篇幅目标、推理策略。
- 不在空闲时（没有回合在跑）主动发摘要请求：用户不在场时不产生费用。
- 子代理的上下文保护不纳入本方案。

## 影响

- 新模块（建议 `packages/agent-runtime/src/mc-background-compaction.ts`）管理“一份待安装的摘要”：边界、生成状态、失效判断、取消。`runtime.ts` 在 `prepareNextTurn()`、新提问入口和 `performCompaction()` 各接一处。
- 设置项进共享类型、设置页和 `packages/i18n`。
- 费用：预生成后被丢弃的摘要是净增加的费用。丢弃率无法在开发阶段估计，只能靠第 8 条的日志在真实使用中统计。
- 竞态面：预生成期间的历史改写、模型切换、Stop、进程关闭，都要有取消与清理的用例。

## 验收（实现时）

假模型流覆盖：预生成完成后到线即安装且不再发请求；到线时仍在生成；安装后仍超线则丢弃并内联压缩；第 4 条每个失效条件；Stop 与销毁时请求被取消、定时器和监听被清理；用量含后台请求；开关关闭时行为与现状逐事件一致。

## 实现记录（2026-11-11）

| 项 | 实现 |
| --- | --- |
| 规则 | `packages/agent-runtime/src/mc-background-compaction.ts`：何时启动、何时作废、保留用户消息的判断、过期用量锚点 |
| 接线 | `runtime.ts`：`maybePrepareSummary()`（回合边界、未到 90% 时）、`installPreparedSummary()`（经 `performCompaction()`，仅阈值压缩）、`discardPreparedSummary()` |
| 边界 | `buildCheckpoint()` 改为在发摘要请求前记下边界；内联时两者相同 |
| 开关 | 设置项 `backgroundCompaction`，默认关闭；设置 → 默认项里“提前在后台准备上下文压缩”，说明常显 |
| 日志 | `session.compaction.background`：阶段（started / installed / discarded）、作废原因、耗时与 token 数 |

与上面“决定”的差异和补充：

- **第 4 条**：模型调用 `new_context` 时不作废，直接安装已准备好的摘要（它覆盖的正是模型想丢掉的历史）。手动压缩和溢出恢复仍作废后内联重做。
- **第 4 条**：历史改写通过“边界消息是否还在”和“生效中的检查点是否变化”判断；当前实现里改写历史会重建运行时，旧运行时销毁时即取消。
- **安装后的用量读数**：边界之后保留的原文里有助手消息，它们带的服务商用量描述的是安装前的上下文。检查点记录安装时间，早于它的用量不再作为估算锚点，直到新的回复带来用量；重启后仍然有效。
- **R21.2 文件片段恢复**：安装预备摘要时不做。边界之后的原文已经保留，最近读过的文件多半就在其中。
- **保留的用户消息**：安装时如果边界之后已有更新的用户消息，就不再保留旧的那条，避免重放旧请求。
- **并发请求**：摘要请求与正在进行的模型请求同时发往同一服务商，可能更容易触发限流。未实测。

未验证：真实模型与真实服务商；宿主把检查点记录追加在对话文件末尾，而它覆盖的边界在更早的位置，界面上“上下文已压缩”标记的位置没有看过；过期用量锚点只有函数级用例，没有带服务商用量的端到端用例。

## 评审确认（2026-11-11）

| 问题 | 建议 |
| --- | --- |
| 预备线取 80% 是否合适 | 采用 80%；日志记录“预生成启动到安装”的间隔，过短说明要调低 |
| 首个版本默认开还是关 | 关 |
| 到线时仍在生成：等待，还是丢弃后内联重做 | 等待 |

## 重访条件

- R21.3（摘要请求复用提示词缓存）若实现，后台摘要应复用同一请求形状，届时一并调整。
- 丢弃率长期偏高时，改为只在长回合（单回合内用量增长快）里启用。
