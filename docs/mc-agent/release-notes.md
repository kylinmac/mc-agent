# 更新说明流程（PR 模板 → 版本条目 → 发布门禁）

状态：已实施（2026-10-26）。决定记录见 [MC-ADR-0017](adr/mc-0017-post-update-whats-new.md)。本文件只管“写什么、什么时候写、发布时怎么查”；装好新版本后首次启动会弹出该版本的“更新内容”。

## 1. 每个 PR：写「更新说明（用户可见）」

`.github/pull_request_template.md` 规定四节：改动 / 更新说明（用户可见）/ 刻意未改 / 验证。

- **改动** 写给评审：做了什么、为什么，可以有文件名和实现细节。
- **更新说明（用户可见）** 写给最终用户，分三类填：**新功能**（以前做不到、现在能做）、**优化**（已有功能更好用、更少步骤、更安全）、**修复**（以前出错、现在不出错）。哪类没有就删掉那一行；整个 PR 没有用户可见变化就写「无」。
- 合入 PR 时**不改** `mc-changelog`。一个版本常包含多个 PR，逐个 PR 改同一个数组容易冲突，措辞也不统一。

### 怎么写

参照常见桌面软件（Cursor、VS Code、微信）的更新说明：短句、具体、不自夸。

- 一行一件事，写用户得到了什么：能做什么、在哪里、按什么键、什么情况下不再出问题。
- 修复写成「……不再……」或「修复……时……的问题」，说清是哪种情况出错。
- 不写空话：「进一步优化体验」「更加清晰」「全面提升」「更紧凑清晰的样式」这类话看不出改了什么，直接写改了什么；改动小到说不出具体变化，就不写。
- 不写过程和实现：不写「改为」「调整了……逻辑」「重构」、文件名、函数名、PR 号。
- 一般不写「更新内容」弹窗、发版日志本身的样式调整；除非这一版只改了它。
- 行首不加「新功能：」「修复：」或项目符号，界面会按类别分组并加圆点。

| 不要这样写 | 这样写 |
|---|---|
| 更新后弹出的“更新了什么”改为更紧凑清晰的样式。 | （删掉；或这一版只有它时：更新内容弹窗变小，不再遮住大半个窗口。） |
| 关闭时窗口是最大化的，下次打开也会最大化。 | 关闭时若窗口最大化，下次启动仍保持最大化；还原后回到原来的大小。 |
| 进一步优化了会话列表的加载体验。 | 会话很多时，侧边栏打开速度更快。 |
| 修复了一些已知问题。 | 切换会话后，任务栏的折叠状态不再丢失。 |

## 2. 发版前：多个 PR 合成一条版本条目

一个 mc-agent 版本（如 `1.0.23`）在 `packages/shared/src/mc-changelog-zh-CN.ts` 里只有**一条**，按类别分组（类型见 `mc-changelog-types.ts`）：

```ts
{
  version: "1.0.23",          // 不带 v，与标签一致
  date: "2026-10-27",         // 可选
  features: [                 // 新功能
    "语音输入：按住 ⌘⇧Space 说话，松开后文字填入输入框，不会自动发送。",
  ],
  improvements: [             // 优化
    "后台命令结束后，Agent 会自动接着处理结果，不用再手动提醒。",
  ],
  fixes: [                    // 修复
    "关闭时若窗口最大化，下次启动仍保持最大化；还原后回到原来的大小。",
  ],
},
```

弹窗和 设置 → 信息 → 发版日志 都按「新功能 / 优化 / 修复」分组显示，空的类别不显示。

步骤：

1. 列出上一个标签以来合入的 PR：`gh pr list --state merged --base main --search "merged:>=<上个版本日期>"`，或看 `git log v<上个版本>..main --merges`。
2. 收集每个 PR 的「更新说明（用户可见）」，去掉「无」。
3. 合并同类、删掉对用户没意义的细节，按上面的写法改顺，放进对应类别；一般合计不超过 8 行。
4. 全部 PR 都是「无」时也要加一条，只写 `version` 和 `date`：表示有意的静默版本，装好后不弹窗。
5. 英文 `mc-changelog-en.ts` 可选；写了就要与中文每个类别的条数一致，用同样的语气（短句、直接说结果，不用 “seamless”“improved experience” 之类）。中文界面读中文，其他界面语言读英文，缺英文时回落到中文。
6. 这条改动走一个普通 PR（如 `docs: 1.0.23 更新说明`）合入 main，**然后**再打标签。条目必须在标签里，因为安装包里的弹窗只读打包进去的内容。

这里只写 mc-agent 自己的 1.x 版本。上游 PI-Desktop 0.x 的说明在 `packages/shared/src/changelog-*.ts`，同步上游时原样合入，不在里面加 mc-agent 的版本，也不把上游条目搬过来。合入上游带来的用户可见变化，由合并 PR 的「更新说明」挑出要点写进 mc-agent 版本条目。

## 3. 发布门禁

| 位置 | 检查 | 作用 |
|---|---|---|
| Docs check（PR 和 main，`docs-check.yml`） | `node scripts/check-mc-changelog.mjs` | 已有条目的格式：版本 `x.y.z` 且 ≥ 1.0.0、不重复、新版本在前；日期 `YYYY-MM-DD`；只用 `features` / `improvements` / `fixes` 三类，每行是非空字符串、不带项目符号或类别前缀、不含「进一步」「全面提升」「更加清晰」这类空话；英文版本必须在中文里存在且每类条数一致 |
| `mc-agent Release` 的 prepare（`mc-release.yml`） | 在 `v<版本>` 的 worktree 上跑 `check-mc-changelog.mjs --require <版本>` | 标签里没有该版本条目、或有比它还新的条目时失败，**不会创建草稿**，也不会开始构建 |

- `1.0.20`–`1.0.22` 的标签里还是扁平的 `highlights`；脚本对这几个版本仍接受它（`FLAT_HIGHLIGHTS_UNTIL`），重跑它们的发布草稿不会失败。之后的版本必须分类。
- 门禁从 `1.0.20` 开始（脚本里的 `REQUIRED_FROM`）。`v1.0.19` 及之前的标签早于本流程，重跑它们的草稿不受影响；本 PR 不为历史版本补条目。
- 第一条真实条目随第一个用到门禁的版本（`1.0.20` 或之后）一起写。
- 上游的 `scripts/check-release-docs.mjs`（`APP_VERSION` 0.21.0、`changelog*.ts`）不读 `mc-changelog*`，两者互不影响。
- 门禁失败的处理：补条目的 PR 合入 main 后，标签要指向包含条目的提交。标签还没公开发布时可删掉重打；已公开的版本不可覆盖（见[云端发布](cloud-release.md)），只能发下一个版本。

## 4. 发布顺序（补充[云端发布](cloud-release.md)）

1. 功能 PR 按模板写好「更新说明」，通过检查后合入 main。
2. 汇总成版本条目（第 2 节），PR 合入 main。
3. 在该提交上创建并推送 `v<版本>`。
4. `gh workflow run mc-release.yml -f version=<版本>`；prepare 先检查条目，再建草稿、构建、发布。

GitHub Release 页面的正文暂时仍是 `--generate-notes` 自动生成；是否改用同一条目，等弹窗上线后再定。
