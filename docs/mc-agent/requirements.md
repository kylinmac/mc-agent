# mc-agent 需求文档

版本：草案 0.2。已确认产品定位、macOS 首发、Fork PI-Desktop 及接受开源；新增功能与优先级为评审建议，尚未冻结。当前阶段只完善文档。

## 1 产品定位

**一句话**：为工作室、OPC 和多项目开发用户提供以项目管理为核心的桌面 Agent，把项目文档、资源、任务与开发结果组织在一起，让 Agent 基于明确的项目资料开展开发。

| 项目 | 已填写的定位 |
|---|---|
| 目标用户 | 工作室、OPC、多项目开发用户 |
| 主要痛点 | 现有 Agent 对项目的管理不够友好，文档和资源维护较差 |
| 首版成功标准 | 做好项目管理，并利用项目管理更好地开发项目；下文给出可验收的建议 |
| 首发平台 | macOS |
| 模型服务及凭据来源 | 目标是支持 Pi 提供的 API 与登录方式；继承上游，逐项建立兼容验证清单 |
| 产品差异 | 项目管理 |
| 开发底座 | Fork PI-Desktop，接受其开源许可方向 |

工作室是目标用户群，不自动意味着首版需要多人云协作。建议首版先解决单机管理多个项目；协作方式列为待确认。

## 2 产品边界

基础 Agent 直接继承，不重新开发一套。新增价值是：
**项目资料 → 有验收条件的开发任务 → 执行会话 → 产物与验证 → 用户确认完成。**

保留上游已有插件、多 Agent、定时等能力；“首版不扩展”不等于删除。上游声称支持的能力，需经过 macOS 回归才能标为本产品已验证。

详细依据见[功能与缺口分析](pi-desktop-analysis.md)。

## 3 三个核心场景

以下是由定位推导的场景，待你用真实项目确认。

| 场景 | 输入与前置条件 | 用户结果 | 完成判据 |
|---|---|---|---|
| S1 接手一个已有项目 | 本地项目及分散的需求、架构、原型、参考资源 | 一个项目入口可找到资料、状态和相关会话 | 资料能打开，分类明确，已确认版本与草稿不混淆 |
| S2 按文档开发一项功能 | 选定需求资料、目标、验收条件 | 建立任务并启动 Agent，结果可追溯到依据 | 任务能跳转到会话、产物、验证记录；用户确认后完成 |
| S3 多项目切换后继续工作 | 两个项目和一个未完成任务，期间文档有变化 | 继续正确项目，知道上次做到哪、依据是否变化 | 无跨项目串用；变化或缺失明确提示；重启后关联仍在 |

## 4 继承的基础 Agent 能力

以下编号保留原模板含义，作为兼容验收项，不是新建待办。

| 编号 | 继承能力 | 验收重点 |
|---|---|---|
| R1 | 模型、API 和账号登录 | 覆盖所选版本支持范围；登录、刷新、退出、错误均可辨识 |
| R2 | 连续对话与流式输出 | 上下文正确、内容不重复、终态明确 |
| R3 | 文件、命令及其他既有工具 | 保持工具范围和权限，能查看结果 |
| R4 | 审批和模式 | 保留已有权限、Plan／Goal 的授权边界 |
| R5 | 停止 | 区分立即停止与完成当前批次后停止，不承诺自动撤销 |
| R6 | 会话历史、搜索、分支和项目组织 | 不破坏原有数据，重启后可查看 |
| R7 | 错误、恢复及重试 | 不把失败显示为成功，不重复未知副作用 |
| R8 | 运行中插话和消息排队 | 沿用上游时机与归属，不降级为新开发 P1 |

其他已有能力纳入功能清单和变更影响回归；本轮没有证明所有上游能力均可靠可用。

## 5 首版新增需求

建议 P0，确认后才成为开发范围。关联关系和持久化规则见[协议与数据](protocol-data.md)。

| 编号 | 新增能力 | 最小范围 | 通过标准 |
|---|---|---|---|
| R9 | 项目概览 | 目标、资料状态、任务进度、待验收入口 | 从一个入口定位当前任务及阻塞，统计来自实际状态 |
| R10 | 项目资料目录 | 登记已有本地文件与 URL；需求／架构／原型／参考资料分类 | 不搬动原文件；可打开、编辑登记信息和解除关联 |
| R11 | 资料确认与变更提示 | 草稿、已确认、已废弃；确认时记录本地文件内容哈希 | 文件变化后提示“确认版本已变化”，不继续显示为当前已确认 |
| R12 | 项目开发任务 | 稳定 ID、标题、目标、验收条件、引用资料、关联会话 | 跨会话保持同一任务；不以会话标题充当任务身份 |
| R13 | 从任务启动 Agent | 预览资料清单，明确选择后调用已有会话启动路径 | 记录本次依据；缺失必需资料时阻止启动，不静默略过 |
| R14 | 结果与验收 | 关联产物、验证说明、用户验收结果 | Agent 完成后进入待验收；用户确认后才变成已完成 |
| R15 | 失效修复与持久化 | 文件移动／删除、并发修改、关联重开、项目身份变化 | 可修复链接；旧记录可追溯；不误删原文件或串项目 |

补充规则：
- 首版资料正文直接使用原文件；支持 Markdown／纯文本作为任务上下文。其他文件可登记和打开，是否读取由既有能力和权限决定，不承诺 PDF／Office 自动解析。
- URL 首版作为参考链接，不自动抓取网页或承诺远端版本锁定。需要它作为确定依据时，先保存本地快照。
- 任务可关联多次执行；建议每次通过 Desktop 托管会话执行。一次会话完整归属一个项目任务，避免首版复杂映射。
- Agent 可提出任务草案和结果；用户决定任务范围和最终验收。暂不新增自主批量调度器。

## 6 任务状态与异常

建议状态：待办 → 进行中 → 待验收 → 已完成；可转为阻塞或取消，验收不通过回到待办。停止／失败不等于完成，保留已有产物并进入阻塞。

用户可在普通聊天中继续自由使用 Agent；资料确认门槛只适用于“从项目任务启动”的管理流程，不额外限制普通对话。

关联资料变化后标出受影响的任务。运行中的任务继续记录原依据，不自动切换新版本；下次执行重新核对。已完成任务保留历史验收，不因新版本出现自动变成未完成。

## 7 首版不新增的范围

多人云同步、组织权限、复杂排期和依赖图、跨项目自动调度、全量知识库检索、完整在线文档编辑器。多目录项目、记忆、会话待办及现有插件等直接复用。

## 8 质量和验收目标

- 数据：资料文件仍由用户持有；解除关联不删除原文件；外部修改不被静默覆盖。
- 权限：项目资料不升级成系统指令；跨根目录和 worktree 访问遵守既有授权。
- 可追溯：每次任务执行能查到资料清单、确认版本、会话、产物与验收结果。
- 体验：键盘可操作，状态有文字说明，找不到文件时有修复入口。
- 模型：版本、服务和登录范围明确列出，通过与未测分开标注。
- 性能：先用真实样例测量；首版资料数量、单份大小和总上下文预算在开发前确定，不能无限注入。
