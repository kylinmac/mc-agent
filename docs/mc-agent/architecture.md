# mc-agent 架构

当前决定：[MC-ADR-0002](adr/mc-0002-fork-pi-desktop.md)，基于 PI-Desktop Fork 二次开发。MC-ADR-0001 保留为历史，其自建内核、目录和协议方案不再执行。

本文件只描述 R1–R9 的增量设计。已有实现见[现状架构](as-built-architecture.md)，路径见[功能代码索引](code-index.md)，源码基线及验证限制见[功能分析](pi-desktop-analysis.md)。

## 1 继承的技术边界

沿用[现状架构](as-built-architecture.md)中的进程、存储和权限分工，不另建 Agent 循环或产品协议。保留上游 pi-coding-agent 依赖及原生会话路径；消息以锁定版本的实际契约为准。

## 2 项目管理扩展放在哪里

| 需求 | UI | 业务与数据归属 | 复用路径 |
|---|---|---|---|
| R1 项目结构 | 新建／编辑项目、模板管理、起始目录选择 | Host 保存资料目录、模板来源、起始目录记忆；路径校验纳入资料目录；改名时改写路径 | 项目组、`resolve_tool_workspace_for_call`、`session_collaboration`、`data_relocation` 的表清单 |
| R2 项目概览 | ProjectsPage／项目详情 | Host 聚合项目元数据及任务状态 | 既有项目组和会话列表 |
| R3 R4 资料目录与确认 | 项目资料列表、详情与打开入口 | Host 保存关联、校验实际文件与确认版本 | 既有文件访问、Work Panel |
| R6 项目任务 | 任务列表与详情 | Host 保存任务与状态 | 不修改 session_todo 的含义 |
| R7 任务启动与依据 | 启动前资料预览 | Host 核验资料；Main 路由并组装启动参数 | session-launch、host-runtime、agent-runtime |
| R8 结果与验收 | 待验收页、产物链接 | Host 保存执行关联、验收结果 | 既有会话和 artifacts |
| R9 失效与恢复 | 修复提示 | Host 版本校验、迁移与删除规则 | 既有事务和项目生命周期 |

这是增量设计建议，接口名称和表结构尚未冻结。本轮不创建上述模块。

## 3 扩展位置

按[功能代码索引](code-index.md)定位现有项目、会话、IPC 和数据模块，在相邻位置增加项目域逻辑。不建立平行的 ui/、host/、kernel/ 目录，也不借功能开发重排上游工程。

## 4 项目与任务身份

复用上游 ProjectGroup 作为产品项目入口，但不再区分主次（[MC-ADR-0003](adr/mc-0003-equal-workspaces-and-project-home.md)）：

- 项目身份 = 项目组 ID。任务、资料、验收都绑定它，不绑定任何目录路径。
- 项目由若干平等的工作区加一个资料目录组成。上游 `primaryPath` 和 `roots[0]` 校验保留；资料目录作为项目组的一个根，标记 `kind: "resources"` 并占 `roots[0]`，于是它同时是默认起始目录，上游路径校验、会话归属和启动上下文直接生效；界面和插件按 `kind` 过滤（方案 A，见 MC-ADR-0003）。已有项目第一次使用时自动用 `blank` 模板补建。
- 会话的起始目录可以是资料目录或任一工作区，实际执行会话保留自己的路径及 worktree 归属。

注意两种身份不同：项目组有字符串 ID，底层 projects 表有整数 ID，旧项目还有基于路径的 legacy 映射。新增实体需要明确绑定项目组与执行目录，不能把它们都叫 projectId 后混用。

建议首次启用项目管理时，把 legacy 项目通过兼容映射关联到稳定项目组；具体迁移在编码前确认。目录移动、组拆分或删除不能导致任务错误绑定到另一个项目。

## 5 资料目录、模板与起始目录

```text
~/Documents/mc-agent/
  templates/<模板>/        内置 software、blank；可在应用里编辑和新增
  projects/<项目名>/       每个项目的资料目录，一级子目录 = 资料分类
```

- 创建项目：复制模板 → 登记资料目录 → 关联工作区。任一步失败，不留下半个项目。
- 资料列表：Host 扫描资料目录（忽略 `.git`、`.DS_Store` 等），叠加手动登记的工作区文件和 URL。
- 起始目录：每个项目记住上次的选择；启动时给模型的说明改为“本次起始目录 + 同项目其他目录（绝对路径访问）”，只自动加载起始目录的 AGENTS.md。
- 改名：先检查没有运行中的会话，再改目录名，然后在一个事务里改写按路径存储的数据（`projects.path`、`artifacts.path`、排队附件、定时任务配置、worktree）；失败回滚目录名。

## 6 统筹与派工

主会话在资料目录起步，读资料、拆任务；具体开发派给 Worker 会话，每个 Worker 指定同项目的一个工作区作为起始目录，自然加载该处的 AGENTS.md，也能按需用 worktree 隔离。

上游 Worker 创建时沿用父会话目录（`session_collaboration/mod.rs`），需要扩展一个“目标工作区”参数，Host 校验目标属于同一项目。进程内的 Subagent 共用父会话目录，首版不改。

## 6.1 模板迁移（R5）

在资料目录起一个 Plan 模式会话，用户选模板和模型。AI 只读扫描各工作区与资料目录，输出整理计划；用户审批后按计划复制或移动文件。计划、审批和执行都走上游已有的 Plan 路径，不新增执行器。默认复制，不改工作区仓库。

## 7 拟新增的一条执行链

1. 用户在项目下创建任务，选择资料并填写验收条件。
2. UI 显示本次将使用的资料；Host 校验项目、路径、状态、大小和内容版本。
3. Host 建立执行依据记录；Main 使用已有会话启动路径传入上下文。
4. Node runtime 继续使用上游循环；工具执行与审批继续通过既有 Host 边界。
5. 执行事件更新会话；项目层关联此次会话、结果和产物。
6. Agent 结束后进入待验收，用户核对证据后确认完成或退回。

启动部分失败时保留可辨识记录，重试不能重复创建和执行。上下文准备成功不等于模型已执行；具体状态拆分见[协议与数据](protocol-data.md)。

## 8 数据原则

资料正文仍是本地文件，不同时维护数据库正文副本。数据库保存资料登记、确认版本、任务和关联关系；历史执行可保存受大小限制的上下文快照，用于复现当时依据。

建议在既有 Rust 数据层通过独立命名的增量结构保存项目管理元数据，避免把数据塞进 session_todo 或覆盖项目记忆。最终选表还是受约束的 kv，需按查询和迁移方案确认。

上游会话、消息、凭据及原生 Pi 会话继续使用自己的存储。项目任务首版建议只发起 Desktop 托管会话；原生 Pi 会话仍可用，但不承诺支持相同任务关联。

## 9 安全与一致性

- Renderer 不直接读取任意路径、访问 SQLite 或持有模型密钥。
- 上游文件权限与工具审批继续生效；登记资料不意味着给任意目录执行权限。
- 资料身份使用“资料目录或某个工作区 + 相对路径”定位；worktree 内容与原工作区内容不得混为同一版本。
- 资料目录纳入工具路径校验，与工作区同等对待；项目外路径仍走原有授权。Worker 的目标工作区必须属于同一项目。
- 资料按用户提供的上下文处理，不能覆盖权限和系统指令。必需资料读取失败应阻止任务启动，普通可选项目记忆仍保留上游行为。
- 用户验收、模型执行完成、计划执行授权分别保存和展示，互不代替。
- 对同一任务的并发启动／更新有版本与幂等校验；不能仅靠按钮禁用防重复。
- 项目归档不删除资料；物理文件删除应保留独立明确操作。会话删除导致证据失效时显示缺失，不能抹去验收历史。

## 10 跟进上游与发布

正式开发前固定 Fork 基线并记录 upstream 来源；以小范围提交扩展项目域，合并升级时检查协议、数据库迁移和包版本。

本次已发现 shared schema 常量与 Rust schema 版本不同；不能把文档里的旧版本号直接拿来做兼容设计。升级／降级策略、备份和恢复验证是实现前门槛。

未来分发独立应用时，使用自己的应用 ID、数据目录、更新源和签名；默认不自动修改原 PI-Desktop 数据。需要导入时先备份并提供可验证的映射。

## 11 还需冻结的设计

- 项目组与 legacy 数据的稳定关联策略。
- 新增元数据保存位置、迁移、导出和删除语义。
- 必需资料类型、单份大小、总预算和版本快照保留期。
- 任务与会话关系、启动失败补偿及终态映射。
- 项目资料与 worktree 的来源选择规则。
- `kind` 过滤点清单（项目详情、git 分支、插件 `roots`、编辑对话框、移除目录）。
- legacy 项目补建资料目录时转为存储型项目组的迁移与回滚。
- R5 整理计划的格式，以及复制／移动在审批后的执行与失败处理。
- 改名改写路径的范围与回滚。
- Worker 目标工作区参数的契约与校验。

这些细节确认后才开始实现；不以“已经 Fork”代替架构和兼容性验证。
