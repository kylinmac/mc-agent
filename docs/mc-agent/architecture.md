# mc-agent 架构

当前决定：[MC-ADR-0002](adr/mc-0002-fork-pi-desktop.md)，基于 PI-Desktop Fork 二次开发。MC-ADR-0001 保留为历史，其自建内核、目录和协议方案不再执行。

本文件区分“继承的架构”和“拟新增的设计”。源码依据、固定提交及验证限制见[功能分析](pi-desktop-analysis.md)。

## 1 继承的进程与模块边界

```text
React Renderer
    │ preload 提供的受控 IPC
Electron Main
    ├─ 窗口、路由、进程管理、会话启动、OAuth 交互
    ├─ 既有 Host RPC ── Rust Host Core
    │                      ├─ 项目与会话持久化
    │                      ├─ 权限策略与工具执行
    │                      └─ 凭据、插件等系统服务
    └─ 既有 Sidecar 桥接 ── Node Agent Runtime
                           ├─ Pi 模型与 Agent 循环
                           └─ 工具请求经既有桥接回 Host

packages/host-runtime：复用会话编排、事件与持久化协作模块
packages/shared：共享类型、协议和契约
```

具体 IPC、消息与事件以锁定版本为准，不把这张职责图当作新传输协议。现有 pi-coding-agent 依赖和原生会话路径保留，不按旧 ADR 删除。

## 2 项目管理扩展放在哪里

| 需求 | UI | 业务与数据归属 | 复用路径 |
|---|---|---|---|
| R9 项目概览 | ProjectsPage／项目详情 | Host 聚合项目元数据及任务状态 | 既有项目组和会话列表 |
| R10 R11 资料目录与确认 | 项目资料列表、详情与打开入口 | Host 保存关联、校验实际文件与确认版本 | 既有文件访问、Work Panel |
| R12 项目任务 | 任务列表与详情 | Host 保存任务与状态 | 不修改 session_todo 的含义 |
| R13 任务启动与依据 | 启动前资料预览 | Host 核验资料；Main 路由并组装启动参数 | session-launch、host-runtime、agent-runtime |
| R14 结果与验收 | 待验收页、产物链接 | Host 保存执行关联、验收结果 | 既有会话和 artifacts |
| R15 失效与恢复 | 修复提示 | Host 版本校验、迁移与删除规则 | 既有事务和项目生命周期 |

这是增量设计建议，接口名称和表结构尚未冻结。本轮不创建上述模块。

## 3 沿用上游目录

- apps/desktop/src：页面、组件、状态与现有设计系统。
- apps/desktop/electron/main/ipc：受控 UI 调用的注册与路由。
- apps/desktop/electron/main/runtime：会话启动和运行时上下文。
- packages/host-runtime：既有进程和会话编排协作。
- packages/shared：跨层类型和消息契约。
- crates/host-core/src：项目业务规则、元数据持久化与权限。
- packages/agent-runtime：Pi 适配与 Agent 执行。

新增项目域逻辑放在相邻模块，不重新建立 ui/、host/、kernel/ 平行目录，也不借本次功能重排上游工程。

## 4 项目与任务身份

复用上游 ProjectGroup 作为产品项目入口；多目录仍由上游维护，实际执行会话保留自己的项目路径及 worktree 归属。

注意两种身份不同：项目组有字符串 ID，底层 projects 表有整数 ID，旧项目还有基于路径的 legacy 映射。新增实体需要明确绑定项目组与执行目录，不能把它们都叫 projectId 后混用。

建议首次启用项目管理时，把 legacy 项目通过兼容映射关联到稳定项目组；具体迁移在编码前确认。目录移动、组拆分或删除不能导致任务错误绑定到另一个项目。

## 5 拟新增的一条执行链

1. 用户在项目下创建任务，选择资料并填写验收条件。
2. UI 显示本次将使用的资料；Host 校验项目、路径、状态、大小和内容版本。
3. Host 建立执行依据记录；Main 使用已有会话启动路径传入上下文。
4. Node runtime 继续使用上游循环；工具执行与审批继续通过既有 Host 边界。
5. 执行事件更新会话；项目层关联此次会话、结果和产物。
6. Agent 结束后进入待验收，用户核对证据后确认完成或退回。

启动部分失败时保留可辨识记录，重试不能重复创建和执行。上下文准备成功不等于模型已执行；具体状态拆分见[协议与数据](protocol-data.md)。

## 6 数据原则

资料正文仍是本地文件，不同时维护数据库正文副本。数据库保存资料登记、确认版本、任务和关联关系；历史执行可保存受大小限制的上下文快照，用于复现当时依据。

建议在既有 Rust 数据层通过独立命名的增量结构保存项目管理元数据，避免把数据塞进 session_todo 或覆盖项目记忆。最终选表还是受约束的 kv，需按查询和迁移方案确认。

上游会话、消息、凭据及原生 Pi 会话继续使用自己的存储。项目任务首版建议只发起 Desktop 托管会话；原生 Pi 会话仍可用，但不承诺支持相同任务关联。

## 7 安全与一致性

- Renderer 不直接读取任意路径、访问 SQLite 或持有模型密钥。
- 上游文件权限与工具审批继续生效；登记资料不意味着给任意目录执行权限。
- 资料身份使用项目根与相对路径等明确定位；worktree 内容与主目录内容不得混为同一版本。
- 资料按用户提供的上下文处理，不能覆盖权限和系统指令。必需资料读取失败应阻止任务启动，普通可选项目记忆仍保留上游行为。
- 用户验收、模型执行完成、计划执行授权分别保存和展示，互不代替。
- 对同一任务的并发启动／更新有版本与幂等校验；不能仅靠按钮禁用防重复。
- 项目归档不删除资料；物理文件删除应保留独立明确操作。会话删除导致证据失效时显示缺失，不能抹去验收历史。

## 8 跟进上游与发布

正式开发前固定 Fork 基线并记录 upstream 来源；以小范围提交扩展项目域，合并升级时检查协议、数据库迁移和包版本。

本次已发现 shared schema 常量与 Rust schema 版本不同；不能把文档里的旧版本号直接拿来做兼容设计。升级／降级策略、备份和恢复验证是实现前门槛。

未来分发独立应用时，使用自己的应用 ID、数据目录、更新源和签名；默认不自动修改原 PI-Desktop 数据。需要导入时先备份并提供可验证的映射。

## 9 还需冻结的设计

- 项目组与 legacy 数据的稳定关联策略。
- 新增元数据保存位置、迁移、导出和删除语义。
- 必需资料类型、单份大小、总预算和版本快照保留期。
- 任务与会话关系、启动失败补偿及终态映射。
- 项目资料与 worktree 的来源选择规则。

这些细节确认后才开始实现；不以“已经 Fork”代替架构和兼容性验证。
