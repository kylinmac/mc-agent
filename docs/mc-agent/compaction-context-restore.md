# 压缩后的上下文恢复（计划）

2026-10-30 起草，**建议待评审**。编号 X-COMPACT-01～03，确认后转为 R 编号并补验收 V。承接 [R20 压缩契约](compaction-performance.md) 与 kylinmac/mc-agent#59（篇幅按预算、截断重试、用户原话）。

## 背景

压缩后模型只剩摘要和近期原文。摘要漏掉的细节找不回，读过的文件要重新读，每次压缩还要按全价重读整段上下文。参考实现 Claude Code 2.1.114 的做法（本机提取资料：上一级 `codex-v/分析成果/系统提示词/claude/code/04-inline-prompts.txt`、`codex-v/分析成果/claude-code/bundle/main-bundle.beautified.js`）：

| 机制 | 参考实现（源码确认） | mc-agent 现状（源码确认） |
| --- | --- | --- |
| 回查原文 | 接续消息附一句：需要压缩前细节时，去读完整记录的路径 | 原始消息留在 host-core，模型没有读取入口 |
| 附回文件 | 最近 5 个文件，每个 ≤5K、合计 ≤50K tokens；跳过近期原文里已有的；另附计划、技能、工具声明 | 摘要后只附 `<read-files>` / `<modified-files>` 路径列表 |
| 缓存复用 | 摘要请求沿用对话前缀、末尾追加总结指令，命中提示词缓存；无文字时退回普通请求 | 专用系统提示、序列化成一条用户消息、`cacheRetention: "none"`，前缀与对话不同 |

## X-COMPACT-01 压缩后可回查原文

**做法**

- 新增只读工具（暂名 `ContextHistory`），只读**当前会话**、压缩边界 `throughMessageId` 及之前的消息。参数：起止位置或某条消息附近、条数上限、关键词（可选）；返回带消息序号的文本，单次输出受工具预算限制。
- 读取沿用 sidecar 已在用的 `session.get` 窗口参数（`messageBefore` / `messageAround` / `messageLimit` / `contentLimit`，`crates/host-core/src/rpc/mod.rs`）。SQLite 仍只由 host-core 读，不导出文件，不新增 Rust 接口。关键词检索先在 runtime 侧对分页结果过滤；量大时再评估 host-core 检索接口。
- 摘要前缀（`COMPACTION_SUMMARY_PREFIX`，`pi-runtime-messages.ts`）在工具可用时追加一句：摘要缺少确切代码、错误原文或已写内容时，用该工具查压缩前的原文。工具不可用的场景（子代理、远程或非 Agent 模式，按实际声明为准）不加这句。

**边界**

- 不跨会话，不读其他项目；不返回附件二进制和隐藏推理。
- 工具输出照常进入上下文，计入预算；返回内容是历史数据，不当作新指令（工具说明里写明）。

**验证**：工具只读本会话、边界外拒绝、分页与截断、无压缩时的行为、摘要前缀按工具可用性切换；隔离 Electron 走一次压缩后回查。

**待确认**：`session.get` 窗口在长会话下的分页语义与性能（未验证）；工具在懒加载工具声明（ADR 0048）下的激活方式。

## X-COMPACT-02 压缩后附回最近文件内容

**做法**

- 压缩准备阶段已按消息收集 `read` / `edit` / `write` 路径（`pi-runtime-compaction-plan.ts`）。改为同时记下最后一次操作的位置，按时间倒序取候选。
- **跳过近期原文里已有其最新读取结果的文件**。近期原文最多 64K tokens（`context-budget.ts`），很多文件本来就在里面。
- 剩余候选在压缩安装时**重新读取当前内容**，走与 Read 工具相同的执行路径（runtime → sidecar → host-core `tools.execute`，远程工作区照走 `tools.workspaceExecute`），因而沿用工作区路径检查和远程路由；需要审批或读取失败的文件直接跳过，不弹审批。
- 上限先照参考实现：最多 5 个文件，每个 ≤5K tokens（超出时截断并注明），合计 ≤50K，且不超过压缩后腾出空间的一定比例（比例待定）。
- 作为摘要之后的一条上下文消息加入，注明“压缩时重新读取的当前内容，可能与此前看到的不同”。写入检查点，重建上下文时不重复读取。

**边界**

- 不新增读取权限，不读工作区外路径；内容不展示为一次新的工具调用。
- 附回内容计入压缩后的 token 估算，避免压缩完立即再次触发压缩。

**验证**：候选排序、近期原文去重、上限与截断、路径越界和读取失败跳过、远程工作区路由、检查点重建不重读、压缩后不立即再触发。

**待确认**：附件放进检查点还是每次重建时现读（建议前者，行为可复现）；计划文件、技能等其他附回项本轮不做。

## X-COMPACT-03 摘要请求复用提示词缓存

**做法**

1. **先测量**：压缩用量已有 `cacheRead`，在压缩诊断里记录每次摘要的输入、缓存读取和耗时，拿到现状基线后再决定是否实现。
2. **对话形摘要请求**：与上一轮对话相同的系统提示、工具声明和消息格式（同一 `convertToLlm` 与请求头、会话关联），末尾追加一条用户消息承载 #59 的摘要指令；Responses / Codex 沿用同一 `prompt_cache_key`。
3. **退回**：返回工具调用、无文字、被截断或服务商报错时，退回现有专用摘要请求，不计为失败。
4. 仅在整段上下文放得下时使用；分块压缩、超窗缩减路径保持现状。先覆盖 Anthropic Messages 与 OpenAI Responses / Codex，其余服务商保持现状。

**边界**：请求仍带工具声明但不执行工具调用；不改变正常对话请求，不改已保存会话。

**验证**：用本地假服务检查请求前缀与对话逐字节一致、工具调用和无文字退回、截断退回、用量归属；真实服务商的缓存命中率与提速需用户同意后单独测。

**需要你拍板**：Anthropic 等服务商改变推理参数可能使缓存失效（未验证）。“缓存命中”与 R20 的“摘要推理不高于 medium”可能冲突，两种选择：

| 选项 | 效果 |
| --- | --- |
| A 沿用对话推理等级 | 最可能命中缓存；高推理会话的摘要更慢更贵 |
| B 保持不高于 medium | 遵守 R20；部分服务商可能拿不到缓存收益 |

建议先做第 1 步测量，按实测选 A 或 B。
