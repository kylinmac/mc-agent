# 上下文恢复完整性与请求诊断（R25；P8；V69）

状态：2026-11-02 用户追加确认：补齐恢复边界和长历史预算回归，提交新 PR，验证后合并并发版。

## 问题与目标

界面和磁盘有消息，不代表恢复后的模型上下文包含它们。1.0.44 修复了一个具体边界问题；本次增加独立检查，使类似遗漏能在发送前被发现，并留下不含正文的排查证据。

## 实施计划

| 步骤 | 范围 | 验收 |
| --- | --- | --- |
| 1 | 从宿主原始历史按消息 ID 推导检查点后应保留的主会话消息；区分系统、子代理、失败助手、空消息、无效工具记录等已有过滤规则 | 不把合法过滤算丢失；不能用已过滤的结果反推预期 |
| 2 | 恢复时比较预期 ID 与实际上下文中的记录身份及顺序 | 异常时仅重试完整历史一次；仍不完整则停止，不调用模型；历史读取失败也不得静默开启空上下文 |
| 3 | 复用现有诊断通道，记录恢复检查和每次主模型请求的结构 | 恢复关联 ID、检查点及边界指纹、数量、固定过滤原因、异常数量、角色计数、估算 tokens；无正文、思考、工具参数、路径、密钥或原始消息 ID |
| 4 | 回归与真实会话副本 | 注入丢消息／乱序故障，比较连续运行与重启后的关键事实、用户纠正、禁止事项和未完成任务；验证发送前拦截及日志隐私 |
| 5 | 提交 PR | 类型检查、相关与运行时全量测试、宿主诊断接线、文档检查；通过后合并，另行补齐版本说明并发布 |

## 边界与取舍

- 沿用 1.0.44 的旧异常检查点兼容恢复；边界必须同时存在于原始历史和转换后的 entries，优先选择最近可用检查点。独立完整性检查也校验该条件。不修改摘要格式、压缩阈值或数据库。
- 完整性检查针对恢复投影。请求诊断记录的是转换后、供应商适配器前的主模型请求结构，不冒充服务端实际接收的完整字节，也不能证明摘要语义无损。
- 不为正常工具执行、扩展合法改写、附件转换强加“消息条数必须相等”。保留现有扩展与工具配对契约。
- 完整历史回退可能增加一次压缩，仍经过既有预算门禁：发送前尝试压缩；关闭压缩、压缩失败或压缩后仍超出硬限制时阻止主模型请求。保留旧异常检查点作为历史证据；新检查点保存成功后，重启优先使用新的，不再回退完整历史。
- 使用临时副本和假模型，不操作正在使用的实例，不调用真实付费模型。真实模型理解质量留待单独评估。

## 出现答非所问时如何判断

默认数据目录下查看 `~/.mc-agent/logs/app/session.log`，自定义数据目录则查看对应的 `logs/app/session.log`。按会话关联以下事件；日志等级高于 info 时正常事件可能不保留。

| 证据 | 能得出的结论 |
| --- | --- |
| `session.context.restore` 的 `ok=false`，warn 级 | 恢复出的记录身份／顺序异常；查看 `missingCount`、`reordered`、`boundaryMissing` |
| 同一 `requestId` 后续 `attempt=2`、`fallback=true`、`ok=true` | 已放弃检查点，完整历史恢复成功 |
| 恢复持续失败，或历史读取报 `context-validation` | 阻止继续发给模型，不会静默按空历史回答；读取失败可能发生在恢复事件产生之前 |
| `session.context.request` 的 `restoreId` | 关联到恢复事件的 `requestId`；核对主模型请求条数、角色分布、估算 tokens 及检查点指纹 |
| 恢复检查通过但回答仍错误 | 只能排除本检查范围内的恢复遗漏；仍需检查摘要内容、历史检索、后续转换和模型理解 |

请求事件按一次逻辑主模型请求记录，供应商内部重试不另计。只记结构，不提供正文，也不将恢复条数与请求条数不同直接判为丢失。
